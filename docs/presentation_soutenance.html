01
Étape 1 — Sécurité

La porte d'entrée : Keycloak & authentification

Tout commence par l'authentification. Comment le système garantit-il qu'un utilisateur est légitime avant même qu'il n'accède aux données ?

🔐 Le mécanisme OAuth2

L'application ne gère aucun mot de passe en interne. Cette responsabilité est entièrement déléguée au serveur Keycloak.

  • Le frontend React affiche le formulaire de connexion, mais transmet les identifiants directement à Keycloak.
  • La validation : Keycloak vérifie les identifiants dans sa base sécurisée, puis fabrique un passeport inviolable — le jeton JWT.
  • Le filtre Spring Security : à chaque requête, React joint ce JWT. Spring vérifie la signature cryptographique. Si le jeton a été altéré, la requête est rejetée (HTTP 401).
  • L'avantage : pour ajouter une connexion Google ou Microsoft demain, il suffit de configurer Keycloak. Le code React et Java ne change jamais.
02
Étape 2 — Identités

L'écosystème des rôles — Shadow User

Gérer les utilisateurs dans deux bases distinctes (locale et Keycloak) sans jamais les désynchroniser.

👥 Le pattern « Shadow User »

Pour lier un ticket à un auteur, l'utilisateur doit exister dans la base PostgreSQL locale. Mais pour se connecter, il doit exister dans Keycloak.

  • Création centralisée : l'administrateur clique sur « Créer un utilisateur » depuis l'interface React.
  • Double sauvegarde : le service UserService.java persiste l'utilisateur dans PostgreSQL, puis utilise un client REST (KeycloakAdminClient) pour l'injecter dans Keycloak.
  • Le rôle comme attribut : le backend injecte le rôle local (ex. « Résolveur ») en tant qu'attribut utilisateur directement dans Keycloak.
  • La matrice des permissions : à la connexion, le backend lit ce rôle et retourne au frontend une matrice RBAC — qui a le droit de faire quoi.
03
Étape 3 — Données

La naissance d'un incident

De la saisie du formulaire jusqu'à la persistance en base, et le couplage avec le moteur de workflow.

🗂️ Persistance & couplage

Créer un incident ne se résume pas à un simple INSERT. C'est l'étincelle qui allume le moteur de workflow.

  • La réception : le contrôleur Java reçoit l'objet (titre, description, priorité) ainsi que l'email du créateur, extrait du JWT.
  • Sauvegarde physique : l'objet Incident est traduit en SQL par Hibernate (JPA) et inséré dans PostgreSQL. Il reçoit alors un identifiant unique (ex. INC-2026-001).
  • Le couplage : immédiatement après, le service appelle Flowable (étape 4). Le moteur génère un processInstanceId, que le backend persiste dans la table Incident. La donnée physique est désormais couplée à sa logique métier.
04
Étape 4 — Orchestration

Le moteur Flowable & le XML BPMN

Comment un simple fichier XML dicte le comportement de toute l'application.

⚙️ L'interpréteur de XML

Le fichier incident_workflow_v2.bpmn20.xml n'est pas qu'un dessin : c'est du code exécutable. Le moteur Flowable, intégré à Spring Boot, le lit au démarrage.

  • L'avancée pas-à-pas : à la création de l'incident, Flowable positionne un « pion » sur la case Départ. Le pion avance et s'arrête sur une balise <userTask> — une tâche humaine.
  • L'attente : le ticket passe en statut « Nouveau ». Flowable met le processus en pause et l'enregistre dans ses propres tables (ACT_RU_TASK).
  • L'action humaine : un technicien clique sur « Résoudre ». Le backend récupère la tâche en attente et appelle taskService.complete(taskId).
  • L'automatisme : en recevant « Complete », Flowable réveille le pion, lit la flèche suivante dans le XML, exécute éventuellement un script Java, puis s'arrête sur la tâche suivante. La boucle est bouclée.
