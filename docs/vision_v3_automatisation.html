Étape 1 — Scénarios d'Automatisation

Zero-Touch vs Intervention Humaine

L'automatisation ne remplace pas l'humain, elle filtre le bruit. Le système décide intelligemment du routage.

🤖 Scénario 100% Automatisé

Exemple : "Serveur Web Inaccessible." Le moniteur (Zabbix/Prometheus) crée l'incident via notre API. Flowable détecte la criticité technique. Il invoque n8n qui lance un script SSH pour redémarrer le serveur, puis clôture l'incident en base de données. (0 seconde d'intervention humaine).

👨‍💻 L'Exception Humaine (Fallback)

Exemple : "Imprimante physique défectueuse" ou "Échec du script SSH".

  • Si une action physique est requise (remplacer du matériel).
  • Si une validation de sécurité est requise par un manager.
  • Si l'API du prestataire externe (ex: Société X) ne répond pas.

Dans ces cas, le workflow BPMN quitte la boucle d'automatisation et génère une UserTask classique assignée à l'Administrateur local via Keycloak.

Étape 2 — Chantiers Techniques

Impact sur le Code et la Base de données

Quelles modifications devrons-nous apporter concrètement au Frontend, au Backend et à PostgreSQL pour la V3 ?

⚙️ Modifications Backend & DB

  • PostgreSQL : Ajout des colonnes is_automated (boolean), external_ticket_id (varchar), et remediation_logs (text) dans la table Incident pour tracer l'historique des scripts n8n.
  • Spring Boot : Développement d'un nouveau Controller REST WebhookController.java pour recevoir les callbacks asynchrones de n8n (ex: "Ticket clôturé par le prestataire").
  • Sécurité : Ajout de tokens API (API Keys) pour sécuriser les échanges entre Spring Boot et n8n sans passer par l'interface de login React.

🖥️ Modifications Frontend (React)

  • Nouveau Dashboard : Une vue "Supervision IA/Auto" permettant à l'Admin de voir en direct les tickets en cours de traitement par les machines.
  • Lecture seule : Si un ticket est is_automated=true, l'interface React verrouille le bouton "Traiter" pour éviter les conflits humain/machine.
03
Étape 3 — Écosystème

Ressources & Intégrations d'APIs

De quoi a-t-on besoin pour mettre en place ce centre névralgique automatisé ?

📦 Infrastructures & Ressources

L'intégration de la V3 requiert l'ajout du conteneur n8nio/n8n à notre fichier docker-compose.yml, ainsi qu'une base Redis supplémentaire pour gérer la file d'attente des webhooks.

🔌 Les APIs Intégrées (Exemples)

  • Outils ITSM (Société X) : Jira Service Management ou ServiceNow. n8n va utiliser leurs APIs REST pour répliquer nos incidents dans le système du sous-traitant.
  • Communication : Slack API / MS Teams Webhooks. Pour alerter les canaux d'astreinte IT avec des boutons d'actions directs dans le chat (ex: "Approuver le redémarrage").
  • Infrastructure : AWS EC2 / SSH / Ansible. Pour exécuter directement des commandes de redémarrage ou de purge de mémoire si l'incident concerne un serveur.
04
Étape 4 — Bilan V3

Les gains architecturaux

L'impact direct de la séparation des responsabilités entre Java (Métier) et n8n (Intégrations).

🛡️ Découplage Extrême

Le code Java de l'application reste pur. Pas besoin de coder ou de maintenir les SDK officiels de Slack ou Jira dans Spring Boot. L'intégration est déléguée visuellement à n8n.

⏱️ Réduction du MTTR

Le temps moyen de résolution (MTTR) chute. Les incidents critiques notifient les bons experts techniques et leurs systèmes la nuit comme le jour, instantanément.

📈 Évolutivité Facile

Si la "Société X" change d'API, il n'y a plus besoin de recompiler le Backend Spring Boot. Il suffit de modifier le flux visuellement en glisser-déposer sur n8n.
