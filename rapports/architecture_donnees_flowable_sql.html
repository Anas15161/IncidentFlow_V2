Cartographie SQL du Moteur BPMN Flowable (ACT_*)

1. La Nomenclature des Tables Flowable

Le moteur Flowable crée automatiquement ses tables dans votre base PostgreSQL. Pour garantir d'excellentes performances, Flowable divise ses données en trois grands espaces sémantiques. Leurs noms commencent tous par ACT_ (Activity) suivi de deux lettres :

ACT_RE_* (Repository)

Contient les données statiques : les modèles BPMN déployés, le code XML, les images des processus. "Où le workflow est stocké de manière permanente."

ACT_RU_* (Runtime)

Contient les données dynamiques : les processus "En Cours", les tâches actuelles, les variables actives. Ces tables sont vidées dès qu'un processus se termine.

ACT_HI_* (History)

C'est le journal d'Audit. Flowable y archive absolument toutes les actions terminées de manière indélébile. C'est ici que l'historique de votre V1 a été délégué.

2. Où est stocké votre Workflow (BPMN) ?

Lorsque vous dessinez votre processus dans le Modeler et que vous le déployez, Flowable ne crée pas de fichier sur le disque. Il stocke le fichier XML directement dans la base de données (sous forme de ByteArray). Voici la requête SQL pour le vérifier :

-- Liste des modèles de workflow déployés dans le système SELECT ID_, KEY_, NAME_, VERSION_ FROM ACT_RE_PROCDEF; -- Pour voir le fichier XML (BPMN) physique stocké en BDD : SELECT NAME_, BYTES_ FROM ACT_GE_BYTEARRAY WHERE NAME_ LIKE '%.bpmn%';
3. Interroger les Tâches Actives (Runtime)

Lorsqu'un utilisateur déclare un incident, l'application Java demande à Flowable de démarrer une instance. Flowable crée alors une tâche (ex: "Assignation"). Voici la requête SQL pour voir les tickets bloqués à une étape précise :

-- Liste des tâches humaines actuellement en attente d'une action SELECT ID_, PROC_INST_ID_, NAME_, ASSIGNEE_, CREATE_TIME_ FROM ACT_RU_TASK; -- Liste des variables de workflow actuelles (ex: "incidentTitle") SELECT NAME_, TEXT_ FROM ACT_RU_VARIABLE;
4. Extraire le Journal d'Audit (History)

Dans votre V1, vous alimentiez manuellement une table IncidentHistory. Avec Flowable, le suivi des actions est natif. Une fois qu'une tâche est validée, elle disparaît de ACT_RU_TASK et est insérée de façon permanente dans ACT_HI_TASKINST.

-- Retracer l'historique d'un incident spécifique (par Process Instance ID) SELECT NAME_, START_TIME_, END_TIME_, ASSIGNEE_, DURATION_ FROM ACT_HI_TASKINST WHERE PROC_INST_ID_ = '12345' ORDER BY START_TIME_ ASC;
5. Argumentaire Architecte Logiciel
"Le Moteur Flowable agit comme un service complet et autonome (Embedded Engine). En le connectant à ma base de données PostgreSQL, il a automatiquement généré ses 3 grandes familles de tables (RE, RU, HI). Si mon jury souhaite vérifier que le Workflow n'est plus codé en dur en Java, il me suffit de lancer une simple requête SELECT sur la table ACT_RE_PROCDEF via pgAdmin pour leur prouver que le fichier XML modélisant mon processus d'incident est bien sérialisé et sécurisé en base de données."
